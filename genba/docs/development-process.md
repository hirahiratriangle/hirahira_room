# genba 開発プロセス設計（案）

2026年10月 ・ 対象：構想書「GENBA 1現場1リポジトリで、現場で働く人を支える」（2026年10月版）

## 1. 何を作るか：2つの成果物

構想（スライド7）を作り物に分けると、性格の違う2つになる。プロセスもこの2つで分ける。

| 成果物 | 置き場所 | 中身 | 使い始める時期 |
|---|---|---|---|
| **A. 現場テンプレート** | GitHub のテンプレートリポジトリ `genba-template`（新規） | `docs/00_参画前`〜`07_振り返り` の雛形、Issue テンプレート（確認事項・課題・作業）、ラベル（スコープ外・読めない・ナレッジ候補）、入場時チェックリストを Issue として並べる仕組み、目標設定の雛形 | STEP 1 |
| **B. genba アプリ** | このリポジトリ（hirahira_room）の `genba/` | 全 `genba-*` リポジトリを同期し、立場ごとの画面で見せる | STEP 1 の途中から少しずつ |

**STEP 1（メンバー支援）の主役は A。** チェックリスト・用語集・週報・まとめはリポジトリの中で書けば足り、アプリがなくても試せる。アプリは「書いたものが探しやすくなる」「チェックリストの進み具合が見える」といった、書く人が得をする部分から足す（原則01）。

## 2. 進め方の型：Spec Kit 型の仕様駆動

jpcore で使っている GitHub Spec Kit と同じ流れにそろえる。

```
構想書（pptx）
  └→ 憲章 constitution（変わりにくい原則。全機能が守る）
       └→ 機能ごとに  spec（何を・誰のために） → plan（どう作る） → tasks → 実装
            └→ 現場で試す → 振り返り → 構想書・憲章・spec に戻す
```

| 段階 | 書くもの | 誰が決めるか | 置き場所（案） |
|---|---|---|---|
| 憲章 | 設計原則を「開発で守るルール」に言い換えたもの（[constitution.md](constitution.md)） | 構想の持ち主 | `.specify/memory/constitution.md`（Spec Kit 導入後） |
| spec | 立場・その立場が下す判断・使うデータ・公開範囲・受け入れ条件 | 構想の持ち主 | `specs/NNN-機能名/spec.md` |
| plan | モデル・画面・同期方法・テスト方針 | 開発 | `specs/NNN-機能名/plan.md` |
| tasks | 1日以内で終わる単位の作業一覧 | 開発 | `specs/NNN-機能名/tasks.md` |
| 実装 | コード・テスト・マイグレーション | 開発 | `genba/`（アプリ）または `genba-template`（テンプレート） |

### spec に必ず書く項目（genba 固有）

Spec Kit の標準テンプレートに、次の4つを足す。どれも憲章のチェックに使う。

1. **どの立場の、どの判断のための機能か**（構想書の「立場ごとの機能」のどのスライドに当たるか）
2. **使うデータと公開範囲**（スライド9の表のどの行か。「―」の欄を読む機能になっていないか）
3. **書く人の得**（メンバーが書く量が増える機能なら、メンバーが何を得るか）
4. **個人を測っていないか**（集計の単位が現場か。人ごとの件数・量を出していないか）

## 3. リリースの区切り

構想書の「進め方」STEP 1〜4 に、始める前の準備（R0）を足す。**次のリリースに進む条件は、日付ではなく記録が実際に溜まったかで決める**（データがないうちに指標画面を出さない）。

| リリース | 構想の STEP | 作るもの | 進む条件（出口） |
|---|---|---|---|
| **R0 準備** | ― | 憲章の合意、Spec Kit の導入、GitHub Organization と GitHub App の用意 | 決めること 1・3・5・7 が決まっている |
| **R1 テンプレート** | STEP 1 | A 一式：docs 雛形、Issue テンプレート、ラベル、チェックリスト Issue の自動作成、目標設定と振り返りの雛形、懸念の型（事実・解釈・未確認）、言い回し集の初版 | 試行現場1つで2週間、チェックリストの Issue が閉じられ、用語集・週報・1週目のまとめが書かれた |
| **R2 メンバー画面** | STEP 1 | B の土台：GitHub 同期、メンバーのホーム（チェックリストの進み、用語集、「読めない」一覧、まとめ、過去の現場の検索） | 試行現場のメンバーが、リポジトリを直接開くよりアプリを使う理由がある |
| **R3 リーダー画面** | STEP 2 | 詰まりの一覧、「読めない」の受け取り、1週目のまとめ確認、週次共有の一覧、裁量の線、週報が途切れたときの表示 | リーダーが詰まりに気づくのが、口頭で聞くより早くなった |
| **R4 運営指標** | STEP 3 | 現場単位の6指標（滞留日数・約束と実際のズレ・スコープ外・体制のズレ・用語のズレ・週報の提出率） | 3現場以上で記録が溜まっている（決めること 4 が決まっている） |
| **R5 ナレッジ・成長** | STEP 4 | 公開レビュー、業界別の用語辞書、設計判断の先例検索、組織のスキル分布（本人と課長が合意した到達だけを匿名で集計） | 決めること 2・6 が決まっている |

成長基軸は R1 から少しずつ入る：目標設定の雛形と、記録にスキル項目を付ける欄は R1（テンプレート）、目標と到達の表示は R2、スキル分布は R5。

## 4. いまのプロトタイプの扱い

`genba/` にあるプロトタイプ（commit 74dbf95）は、**画面の当たりを付けるための v0** とする。R2 で「GitHub が正、アプリは同期して見せる」形に作り直すので、モデルを延命させない。それまでは、構想の議論のためにデモデータで見せる用途に限る。

更新された構想とのずれ（R2 以降で解消する）：

| 項目 | プロトタイプ | 更新後の構想 |
|---|---|---|
| データの正 | アプリの DB に直接書く | `genba-*` リポジトリが正。アプリは同期 |
| 公開範囲 | 本人が「チーム／会社」を選ぶ。公開の最終判断も本人 | チーム内は全公開。会社へは一般化レビューを通して出す。本人に範囲を選ばせない |
| 原則05 | 記録を評価に使わない | 他人が記録で人を採点しない（本人が証拠として引くのは自由） |
| 文書の種類 | 7種類（独自の分け方） | `docs/00`〜`07` のフォルダに合わせる（業務理解が増える） |
| 週報 | 本文＋課題・リスク | やったこと・分かったこと・詰まり・次 |
| Issue ラベル | スコープ外のみ | ＋読めない・ナレッジ候補 |
| 運営指標 | 5指標 | ＋体制のズレ（6指標） |
| チェックリスト・まとめ・言い回し集・裁量の線 | なし | メンバー支援kit の中心 |
| 成長基軸 | 振り返りにスキル対応の文字列だけ | 目標（11スキル項目×レベル）→ 記録にスキル項目 → 到達 → 課長と合意 → スキル分布 |
| 立場 | 4つ | 4つ＋到達を合意する「課長」の関わり（立場として持つかは R5 の spec で決める） |

当面の扱い（案）：HOME のアプリ一覧には「プロトタイプ」と書いて残す。本番に出す前に、デモデータを入れたままにしないことを確認する。

## 5. 1つの機能が終わる条件（Definition of Done）

- [ ] spec の受け入れ条件をすべて満たす
- [ ] 憲章のチェック（[constitution.md](constitution.md) の「レビューで確かめること」）を通った
- [ ] 公開範囲のテストがある：その立場が読んではいけないデータ（原文、個人名、他の現場）が画面に出ないことを確かめるテスト
- [ ] `python manage.py test genba` と、全体の `python manage.py test` が通る
- [ ] マイグレーションがあれば、本番（Azure）での実行手順を PR に書いた（`deploy.txt` の手順に沿う）
- [ ] 画面のある機能は、デモデータでのスクリーンショットを PR に貼った

## 6. ブランチ・レビュー・リリース

このリポジトリの既存のやり方に合わせる。

- **ブランチ**：機能ごとに1本（例：`genba/002-checklist-sync`）。spec の番号とそろえる。
- **PR**：spec・plan へのリンク、憲章チェックの結果、スクリーンショットを載せる。
- **リリース**：`main` に入れたあと `./deploy.sh`。マイグレーションは Azure 上で実行。
- **テンプレート（A）**：`genba-template` リポジトリ側で同じ流れ。変更したら、作成済みの現場リポジトリに反映するかを PR で決める（既存の現場には自動で反映しない）。

## 7. 現場で試して戻す

各リリースの最後に、試行現場で使ってもらい、次の3つを構想に戻す。

1. **書かれたか**：用語集・週報・まとめ・Issue が実際に書かれたか（現場単位で見る。誰が何件書いたかは見ない）
2. **得をしたか**：メンバーに「書いてよかった場面」を聞く
3. **書きにくかったこと**：書かなかった理由。型（事実・解釈・未確認）で足りるか、別のチャネル（1on1）に回すべきか

戻し先：構想書（方向が変わるとき）→ 憲章（原則が変わるとき）→ 次の機能の spec（細部）。

## 8. 決めること（構想書スライド22）とリリースの対応

| # | 決めること | 決まらないと止まるリリース |
|---|---|---|
| 1 | GitHub の Organization を会社で持つか、誰が管理するか | R0（GitHub App・同期の前提） |
| 2 | 会社公開の一般化レビューを、誰がどの粒度で行うか | R5 |
| 3 | 「他人が記録で人を採点しない」を規程にするか、運用ルールにするか | R0（試行の前にメンバーへ約束する） |
| 4 | 運営指標と組織のスキル分布を、見られる人の範囲 | R4・R5 |

| 7 | 最初に試す現場とメンバー | R0 |
