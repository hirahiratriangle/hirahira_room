# genba 開発プロセス設計

2026年10月 ・ 対象：構想書「GENBA 1現場1リポジトリで、現場で働く人を支える」（2026年10月版）

## 0. 前提（決定済み）

| 項目 | 決定 |
|---|---|
| 進め方 | Spec Kit 型の仕様駆動（憲章 → spec → plan → tasks → 実装） |
| 憲章の範囲 | genba 専用。hirahira_room の他のアプリには適用しない |
| 目的 | **プロトタイプ**。構想を説明する資料として動けばよい。GitHub の実物（Organization・テンプレートリポジトリ・同期）は作らない |

## 1. 何を作るか

構想（スライド7）では、成果物は「現場テンプレート（`genba-template` リポジトリ）」と「アプリ（hirahira-room）」の2つ。プロトタイプでは**両方をアプリの中で見せる**。

| 構想の成果物 | プロトタイプでの見せ方 |
|---|---|
| 現場テンプレート（docs 00〜07、Issue テンプレート、ラベル、チェックリスト） | アプリの中に「テンプレート」を持つ。現場を作ると、docs の区分とチェックリストの項目がその現場に並ぶ |
| `genba-*` リポジトリ（1現場＝1リポジトリ） | アプリの「現場」。リポジトリ名は表示用に持つ |
| GitHub 同期 | 作らない。記録はアプリの DB に書く |
| 立場ごとの画面 | そのまま作る |

本番化（GitHub を正にする）は、このプロセスの対象外。構想が固まったあとに別に計画する。

## 2. 進め方の型

```
構想書（pptx）
  └→ 憲章（genba/docs/constitution.md）
       └→ 機能ごとに spec → plan → tasks → 実装
            └→ デモで構想を説明できるか確かめる → 構想書・憲章・spec に戻す
```

### ファイルの置き場所

憲章を genba 専用にするため、Spec Kit の CLI はリポジトリ直下に入れず（`.specify/` や `.claude/commands/` は hirahira_room 全体に効くため）、**同じ書式のファイルを `genba/` の中に置く**。

```
genba/
├── docs/
│   ├── constitution.md          憲章
│   └── development-process.md   この文書
└── specs/
    └── NNN-機能名/
        ├── spec.md    何を・誰のために（構想の持ち主が承認）
        ├── plan.md    どう作る
        └── tasks.md   作業の一覧
```

### spec に必ず書く項目（genba 固有）

Spec Kit の標準の項目（ユーザーストーリー、受け入れ条件、範囲外）に、次の5つを足す。

1. **対応する構想書のスライド**（デモで説明する範囲）
2. **どの立場の、どの判断のための機能か**
3. **使うデータと公開範囲**（スライド9の表のどの行か）
4. **書く人の得**（メンバーが書く量が増えるなら、何を得るか）
5. **憲章チェック**（個人を測っていないか、など）

## 3. 作る順番

構想書の「進め方」（メンバー支援 → リーダー → 運営指標 → ナレッジ公開）の順に、spec を切る。各 spec の出口は「**デモデータで、対応するスライドの内容を画面で説明できる**」こと。

| spec | 立場 | 中身 | 説明できるようになるスライド |
|---|---|---|---|
| **001 メンバー支援kit**（実装済み） | メンバー | 現場テンプレート（docs 00〜07・ラベル）、入場時チェックリスト、「読めない」一覧、1週目のまとめ、週報の型、懸念の型、用語集、言い回し集、危険信号 | 7, 12, 15, 16 |
| **002 成長基軸（メンバー）**（実装済み） | メンバー | スキルセット（11項目×レベル）、入場前の目標、記録へのスキル項目、振り返りで到達を説明 | 5, 13, 14 |
| **003 リーダー画面**（実装済み） | リーダー | 詰まりの一覧、「読めない」の受け取り、まとめ確認、週次共有、裁量の線、懸念の受け取り | 17 |
| **004 運営指標**（実装済み） | マネジメント | 現場単位の6指標（体制のズレを追加） | 18 |
| **005 ナレッジ資産と成長のつながり**（実装済み） | 会社 | 公開レビュー（一般化）、業界別用語辞書、先例検索、質問リスト、組織のスキル分布、立場ごとの成長 | 6, 19, 20, 21 |
| **006 到達の確定とスキル台帳**（実装済み） | 全立場 | 記入・確認・承認、ひとり現場、個人のスキル台帳、証拠つきスキルシート | 4, 8, 9, 20, 22 |

全体（スライド4・8・9）は、すべての spec に共通する前提として憲章で守る。

## 4. いまのプロトタイプとの関係

`genba/` のプロトタイプ（commit 74dbf95）を土台に、spec ごとに直していく。更新された構想とのずれと、直す spec：

| 項目 | いまのプロトタイプ | 更新後の構想 | 直す spec |
|---|---|---|---|
| 文書の種類 | 7種類（独自の分け方） | docs 00〜07 のフォルダに合わせる | 001 |
| 週報 | 本文＋課題・リスク | やったこと・分かったこと・詰まり・次 | 001 |
| Issue ラベル | スコープ外のみ | ＋読めない・ナレッジ候補 | 001 |
| チェックリスト・まとめ・言い回し集・危険信号 | なし | メンバー支援kit の中心 | 001 |
| 懸念の書き方 | 自由記述 | 事実・解釈・未確認に分ける | 001 |
| 成長基軸 | 振り返りにスキル対応の文字列だけ | 目標 → 記録のスキル項目 → 到達 → 課長と合意 | 002・005（済） |
| 運営指標 | 5指標 | ＋体制のズレ（＋リーダーの懸念・週報の途切れの継続） | 004（済） |
| 公開範囲 | 本人が「チーム／会社」を選び、公開も本人が決める | チーム内は全公開。会社へは一般化レビューを通して出す | 005（済） |
| 原則05 の文言 | 記録を評価に使わない | 成長を評価し、支援する | 006 |
| 到達の確定 | 本人の依頼で課長と合意 | 記入・確認・承認 | 006 |
| 会社 | 合意した到達の匿名集計 | 個人のスキル台帳 | 006 |

## 5. 1つの spec が終わる条件（Definition of Done）

- [ ] spec の受け入れ条件をすべて満たす
- [ ] 憲章の「レビューで確かめること」を通った
- [ ] 公開範囲のテストがある（その立場が読んではいけないデータが画面に出ない）
- [ ] `python manage.py test genba` と全体の `python manage.py test` が通る
- [ ] `seed_genba` のデモデータを更新し、対応するスライドを画面で説明できる
- [ ] 画面のスクリーンショットを残した

## 6. ブランチ・コミット

- ブランチ：いまは `claude/genba-inquiry-m0e4mz` で進める。spec ごとにコミットを分ける。
- 本番（Azure）に出すかは別に判断する。出す場合はデモデータを入れたままにしない。

## 7. 構想に戻す

spec を1つ終えるごとに、デモを見て次の3つを確かめ、構想書・憲章・次の spec に戻す。

1. **説明できたか**：スライドの内容が画面で伝わるか
2. **書く人が得をするか**：メンバーの画面が「書かされる道具」に見えていないか
3. **構想の穴**：作ってみて、構想書に書かれていない判断が要ったところ（spec の「未決事項」に残す）

## 8. 決めること（構想書スライド23）の扱い

プロトタイプでは、決まっていないことは**仮の前提を置いてデモに反映し、spec に「仮」と書く**。

| # | 決めること | プロトタイプでの扱い |
|---|---|---|
| 1 | GitHub の Organization を会社で持つか、誰が管理するか | 対象外 |
| 2 | 一般化レビューを誰がどの粒度で | 仮：リーダーが確認する（005） |
| 3 | ひとり現場の確認を担う自社リーダー | 仮：マネジメントが確認と承認を行う（006） |
| 4 | 運営指標とスキル台帳を見られる人 | 仮：マネジメント・会社のグループ（004・006） |
| 5 | 顧客の NDA と GitHub | 対象外 |
| 6 | 到達を評価・職級・スキルシートにどうつなぐか | 仮：承認でレベルと評価A〜Eを決め、スキルシートの文章を出す（006） |
| 7 | 最初に試す現場とメンバー | 対象外（デモデータで見せる） |
