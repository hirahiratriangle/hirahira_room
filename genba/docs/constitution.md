# genba 憲章（案）

構想書の設計原則（スライド8）とデータの公開範囲（スライド9）を、開発で守るルールに言い換えたもの。すべての spec・plan・PR はこの憲章に照らしてレビューする。Spec Kit 導入後は `.specify/memory/constitution.md` に置く。

## 原則と、開発で守るルール

### I. メンバーの道具が先（原則01）

管理・指標・資産は、メンバーの記録の副産物として得る。

- メンバーが書く量を増やす機能は、spec に「書く人の得」を書く。書けないなら作らない。
- 上の立場の画面のために、メンバーに新しい入力欄を足さない。必要な数字は、既にある記録から数える。

### II. 人ではなく現場を測る（原則02）

- 集計の関数・クエリ・API は、現場（リポジトリ）単位の値だけを返す。人ごとの件数・記述量・作業量・稼働時間を返すものを作らない。
- 使わない指標（個人のコミット数・Issue 作成数・記述量、個人別の稼働時間の比較、振り返りの文章による個人評価）は、内部の集計にも作らない。

### III. 公開を前提に書く（原則03）

- 現場チーム（メンバーとリーダー）の中では、記録は全文を読める。本人に公開範囲を選ばせる欄は作らない。
- 会社への公開は、一般化レビュー（ナレッジ候補 → リーダーが一般化を確認 → 公開）を通ったものだけ。会社公開の画面に、顧客名・固有の業務名・個人名を出さない（業界名で置き換える）。

### IV. 上の立場ほど集計で見る（原則04）

公開範囲は次の表が正。画面・API はこの表を超えて見せない。「―」は見せない。

| データ | 現場チーム | マネジメント | 会社全体 |
|---|---|---|---|
| 面談メモ・言葉のズレ | 全文 | ズレの件数 | 一般化して公開 |
| 作業範囲・約束事項 | 全文 | 約束と実際のズレ件数 | ― |
| 単価・契約金額 | 置かない | ― | ― |
| 用語集 | 全文 | 用語のズレ件数 | 一般化して公開 |
| 設計メモ | 全文 | ― | 一般化して公開 |
| 体制・議事録 | 全文 | 体制のズレ件数 | ― |
| 週報・Issue | 全文 | 提出率・滞留日数 | ― |
| 振り返り | 全文 | 現場単位の集計 | 一般化して公開 |

- 立場ごとの見え方は、テストで確かめる（読んではいけないデータが出ないこと）。

### V. 記録で人を採点しない（原則05）

- 本人が自分の記録を成長の証拠として引くのは自由。他人が記録を拾って評価する機能は作らない（例：ある人の記録を一覧にして点を付ける画面）。
- 組織のスキル分布に使うのは、本人と課長が合意した到達だけ。匿名で集計する。

### VI. 顧客情報と金額は置かない（原則06）

- 単価・契約金額・精算の欄を、モデル・テンプレート・Issue テンプレートに作らない。
- 顧客の成果物・ソースコード・個人情報を取り込む機能（添付・同期）を作らない。同期するのは `genba-*` リポジトリの自分たちの記録だけ。

## 開発の決まり

- **データの正は GitHub**：記録は `genba-*` リポジトリにあり、アプリは同期して見せる。アプリ側だけに記録の原本を持たない（R2 以降）。
- **順番**：メンバー支援 → リーダー → 運営指標 → ナレッジ公開。記録が溜まる前に、上の立場の画面を出さない。
- **テスト**：公開範囲・集計単位に関わる変更には、必ずテストを付ける。

## レビューで確かめること

PR ごとに次を確認し、PR の本文に結果を書く。

- [ ] 人ごとの数字を出していない（II）
- [ ] 本人に公開範囲を選ばせていない。会社公開は一般化レビューを通る（III）
- [ ] 公開範囲の表を超えて見せていない。そのテストがある（IV）
- [ ] 記録で他人を採点する使い方ができない（V）
- [ ] 金額・顧客の成果物・個人情報の置き場を作っていない（VI）
- [ ] メンバーが書く量が増えるなら、書く人の得が spec にある（I）

## 改訂

この憲章を変えるのは、構想書の原則が変わったときだけ。改訂したら版と日付を残し、影響する spec を見直す。
