# genba 憲章

構想書の設計原則（スライド8）とデータの公開範囲（スライド9）を、開発で守るルールに言い換えたもの。genba 専用で、hirahira_room の他のアプリには適用しない。すべての spec・plan・コミットはこの憲章に照らしてレビューする。

## 原則と、開発で守るルール

### I. 会社が人を支える（原則01）

弱いところを補い、目指す姿を示す。支援kit・指標・資産はそのためにある。

- メンバーが書く量を増やす機能は、spec に「書く人の得」を書く。書けないなら作らない。
- 上の立場の画面のために、メンバーに新しい入力欄を足さない。必要な数字は、既にある記録から数える。

### II. 運営は現場単位で測る（原則02）

- 運営指標は現場（リポジトリ）単位の値だけを返す。人ごとの件数・記述量・作業量・稼働時間を返すものを作らない。
- 個人は運営指標ではなく、成長基軸（承認した成長）で見る。

### III. 公開を前提に書く（原則03）

- 現場チーム（メンバーとリーダー）の中では、記録は全文を読める。本人に公開範囲を選ばせる欄は作らない。
- 会社への公開は、一般化レビュー（ナレッジ候補 → リーダーが一般化を確認 → 公開）を通ったものだけ。会社公開の画面に、顧客名・固有の業務名・個人名を出さない（業界名で置き換える）。

### IV. 上の立場ほど集計で見る（原則04）

現場の記録の原文はチームまで。成長は個人ごとに見る。公開範囲は次の表が正。画面・API はこの表を超えて見せない。「―」は見せない。

| データ | 現場チーム | マネジメント | 会社全体 |
|---|---|---|---|
| 面談メモ・言葉のズレ | 全文 | ズレの件数 | 一般化して公開 |
| 作業範囲・約束事項 | 全文 | 約束と実際のズレ件数 | ― |
| 実際の単価・契約金額 | 置かない | ― | ― |
| 階級・人月（月次） | 全文 | 現場ごとの標準売上・標準粗利 | 全社と業界ごとの標準売上・標準粗利 |
| 階級表（標準単価・標準原価）・在籍人数 | 階級と標準売上まで | 現場ごとの集計まで | 全文（経営層リポジトリに置く） |
| 用語集 | 全文 | 用語のズレ件数 | 一般化して公開 |
| 設計メモ | 全文 | ― | 一般化して公開 |
| 体制・議事録 | 全文 | 体制のズレ件数 | ― |
| 週報・Issue | 全文 | 提出率・滞留日数 | ― |
| 振り返り | 全文 | 現場単位の集計 | 一般化して公開 |
| 目標と成長 | 全文 | 個人ごと（承認する） | 個人のスキル台帳 |

- 立場ごとの見え方は、テストで確かめる（読んではいけないデータが出ないこと）。

### V. 成長を評価し、支援する（原則05）

- 成長は記入（メンバー）・確認（リーダー）・承認（マネジメント）で確定する。ひとり現場はマネジメントが確認も行う。
- 評価・スキル台帳・アサインに使うのは承認した成長だけ。見るのは記録の量ではなく成長。

### VI. 顧客情報と実際の金額は置かず、標準値で積み上げる（原則06）

- 実際の単価・契約金額・精算・給与の欄を、モデル・テンプレート・Issue テンプレートに作らない。これらは別のシステムの話とする。
- 経営の数字の元は、会社が定める階級（標準単価・標準原価）と、現場ごと・人ごとの月次の人月だけ。階級は会社が決め、人月は本人が入れる。これは I の「新しい入力欄を足さない」の例外で、自分の階級と現場への貢献が見えることを書く人の得とする。
- 標準売上と標準粗利は、メンバー → リーダー（現場）→ マネジメント（全現場）→ 会社（全社）へ足し上げて求める。上の立場の金額を別に入力しない。どの段階の合計も、下の段階の合計と一致する。
- 標準原価と在籍人数は経営層リポジトリに置き、現場チームには見せない。
- 標準売上・標準粗利を、人を比べる数字にしない。
- 顧客の成果物・ソースコード・個人情報を取り込む機能（添付・同期）を作らない。置くのは自分たちの記録だけ。

### VII. タスクの消化と成長は両輪で、メンバーの成長が会社の成長を決める（全原則の前提）

構想の「会社の成長は、人から始まる」を、開発で守るルールにしたもの。

- タスクの消化と成長を切り離さない。やり遂げた作業は成長の証拠になる。
- 会社の成長の数字は、メンバーの成長から説明できるようにする。承認した成長は、階級の見直しを通して標準単価と標準売上に届く。
- 階級を定めるのは会社の役割で、自動では上げない。マネジメントが提案し、会社が決める。
- 画面の順序は因果に合わせる。成長を原因、売上を結果として置く。
- 売上の伸びは、人数が増えた分と人が育った分を分けて見せる。

## 開発の決まり

- **プロトタイプ**：構想を説明できることを優先する。GitHub の実物と同期は作らず、記録はアプリの DB に書く。本番化するときは「データの正は `genba-*` リポジトリ」に改める。
- **順番**：メンバー支援 → リーダー → 運営指標 → ナレッジ公開。記録が溜まる前に、上の立場の画面を出さない。
- **テスト**：公開範囲・集計単位に関わる変更には、必ずテストを付ける。

## レビューで確かめること

spec の承認時と、実装のコミット前に次を確認する。

- [ ] 運営指標に人ごとの数字を出していない（II）
- [ ] 本人に公開範囲を選ばせていない。会社公開は一般化レビューを通る（III）
- [ ] 公開範囲の表を超えて見せていない。そのテストがある（IV）
- [ ] 評価に使うのは承認した成長だけ。記録の量で人を見ない（V）
- [ ] 顧客の成果物・個人情報・実際の金額の置き場を作っていない。標準値は階級 × 人月から足し上げ、上の段階で別に入力していない（VI）
- [ ] メンバーが書く量が増えるなら、書く人の得が spec にある（I）
- [ ] 新しい経営の数字は、メンバーの成長またはタスクの消化から説明できる。切れていない（VII）
