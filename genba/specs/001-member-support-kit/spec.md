# spec 001：メンバー支援kit

状態：**実装済み** ・ 2026年10月（未決事項 2〜4 は案のとおりで承認）

## 元資料

| 資料 | この spec で使うところ |
|---|---|
| 入場時チェックリスト上流編 | チェックリストの全項目（1〜4章）、危険信号（5章）、確認のための言い回し（6章）、まとめ・週報・懸念の書き方 |
| SI業界ワード確認表 | 言い回し集の「ワード確認表」（6分類・30語の「一般的な意味」「大切にしたいこと」「使い方の例」） |

アプリに載せるときは、元資料にある特定の顧客名・案件名（前回の現場の名前など）は載せず、教訓の中身だけを残す（憲章 III・VI）。

## 構想との対応

| 項目 | 内容 |
|---|---|
| 対応するスライド | 7（仕組み）、12（入場時チェックリスト）、15（理解を形にする道具）、16（危険信号） |
| 立場 | メンバー |
| 支える判断 | 今日何を確かめ、誰に聞くか。何が読めていないか。理解を形にして見せられているか |
| 使うデータ（スライド9） | 面談メモ・言葉のズレ／作業範囲・約束事項／用語集／設計メモ／体制・議事録／週報・Issue |
| 公開範囲 | すべて現場チーム内で全文。この spec では会社公開・マネジメント向けの画面は作らない |

## 書く人の得

メンバーが書くものは増えるが、どれも「入場直後に迷わない」ための道具として返ってくる。

- チェックリストに沿えば、最初の2週間に何をすればよいかが分かる
- 「読めない」を残すと、2日動かないときに質問へ進むきっかけになる
- 用語集・読めない一覧・未解決の質問が、そのまま1週目の「まとめ」の材料になる（書き直さなくてよい）
- 言い回し集で、期待値・決裁者・契約外の依頼をどう切り出すかに迷わない

## ユーザーストーリー

### US1 現場をテンプレートから作る（スライド7）

現場を作ると、テンプレートどおりの構成がその現場に並ぶ。

- docs の区分：`00_参画前`、`01_契約・条件`、`02_体制`、`03_業務理解`、`04_設計`、`05_議事録`、`06_週報`、`07_振り返り`
  - 各区分に「書くこと」を表示する（例：`01_契約・条件` は「作業範囲と約束事項（金額は置かない）」）
- Issue の種類：確認事項・課題・作業
- Issue のラベル：スコープ外・読めない・ナレッジ候補
- 現場の一生：テンプレートから作成 → 記録 → 振り返り → Archive（状態として持つ。Archive した現場は読むだけ）

### US2 入場時チェックリストに沿って動く（スライド12）

現場を作ると、入場時チェックリスト上流編の項目が、**小見出しごとに1つの「作業」Issue（中にチェック項目）** として並ぶ。GitHub の Issue のタスクリストと同じ形にする。

| 段階 | ねらい（元資料の章の冒頭） | Issue（小見出し） | 項目数 | 残す場所 |
|---|---|---|---|---|
| 入場前（自社営業・課長と確認） | 契約と現場の進め方のずれを、入場前に言葉で確かめる | 契約・商流／役割と期待値／自社側の支援 | 5／5／2 | 00_参画前・01_契約・条件 |
| 初日 | 組織図と実際の決裁の流れを、一枚のメモにする | 体制と人／ドキュメントと環境／自分の進捗管理をはじめる／初日に聞いておく一言 | 4／5／4／2 | 02_体制・作業 Issue（進捗表） |
| 1週目 | 担当機能と全体像を自分の言葉で説明できる状態を、成果物として見せる | 全体像（1〜2日目）／担当機能（3〜4日目）／「読めない」を放置しない／理解の「まとめ」を出す（5日目） | 3／3／2／3 | 03_業務理解・04_設計・まとめ |
| 2週目以降 | 進捗と懸念は、聞かれる前に自分から定期的に出す | 2週目以降 | 6 | 06_週報・課題 Issue |

計 12 Issue・44 項目。

- メンバーは、段階ごとの進み具合（済みの項目数／全体）を自分の現場のページで見られる
- 各 Issue から、残す場所（docs の区分、「読めない」・課題 Issue の作成、まとめ、進捗表）へ移れる
- 「問われるスキルを選び、目標を立てる」は、スライド12にあり元資料にはない。入場前の「役割と期待値」に1項目足して並べるだけにし、目標の中身は spec 002 で作る

### US2-b 進捗表（元資料 2章「自分の進捗管理をはじめる」）

- 作業 Issue に **予定日** と **完了日** を持たせ、現場のページに進捗表（予定と実績の差）を出す
- 初日の時点では、最初のタスクを「確認作業」そのものにする（チェックリストの作業 Issue が、そのまま進捗表の最初の行になる）
- 遅れが出た作業には「原因と追いつく見込み」を書ける（週次共有に使う）

### US3 「読めない」を残す（スライド15・16）

- 「読めない」ラベルの Issue に、**どの資料の・どこが・なぜ読めないか**（用語／前提／図がない）を書ける
- 現場のページに「読めない」一覧を出す
- 2日経っても解決しない項目には「一覧を持って質問の時間をもらう」目安と、言い回し「読めない資料を上げる」を出す

### US4 1週目の「まとめ」を組み立てる（スライド15）

- 元資料どおり、まとめは **全体像の図・担当機能の整理・用語集・未解決の質問一覧** を1つの資料にしたもの
  - 本人が書く欄：**全体像**（システムの目的・利用者・業務の流れ。文章か図へのリンク）、**担当機能の整理**（入力・処理・出力・データ、つながる機能）
  - 現場の記録から自動で並べる欄：**用語集**、**未解決の質問**（確認事項 Issue）、**読めない一覧**
- まとめを「出した」状態にでき、「リーダーと15分で確かめた」「期待値との差と2週目の作業」を書ける（チェックリストの「理解の『まとめ』を出す」と連動）
- まとめの画面に言い回し「理解を確かめる」を出す

### US5 週報と懸念を型で書く（スライド15・16）

- 週報は **やったこと・分かったこと・詰まっていること・次にやること** の4欄（対象週は月曜にそろえる）
- 課題 Issue は、懸念を **事実・自分の解釈・未確認のこと・影響** に分けて書ける（人ではなく事実と影響を書く、という注意を表示する）
- 課題 Issue の画面に言い回し「違和感を伝える」を出す

### US6 用語集とズレの確認（スライド15）

- 分からない語も、意味を空のまま載せられる（「意味を確認中」と表示）
- 「一般的な意味との違い」を書ける（用語のズレ）
- 同じ語が他の現場でどう使われたかを引ける（他の現場の分は、会社公開されたものだけ）

### US7 言い回し集（スライド15）

テンプレート側（全現場共通）に持ち、2つの面で引ける。

- **確認の言い回し**（チェックリスト 6章の8場面）：期待値を聞く／決裁者を確かめる／読めない資料を上げる／理解を確かめる／裁量の線を引く／違和感を伝える／暗黙の期待を言葉にする／契約外の依頼
- **SI業界ワード確認表**（6分類・30語）：語ごとに「現場での一般的な意味」「大切にしたいこと」「使い方の例」。冒頭の「読み方」と末尾の「全体を通じて大切にしたいこと」も載せる
- 用語集の「一般的な意味との違い」と同じ考え方なので、用語集の画面からワード確認表へ移れる

### US8 危険信号（スライド16）

元資料 5章の7つの兆候と「その日にやること」を、メンバーのホームと現場のページに出す。記録から判定できる3つは、当てはまったときに強調する。

| 兆候 | 判定（プロトタイプ） | その日にやること（元資料） |
|---|---|---|
| 3日経っても理解が進んでいない | 「読めない」Issue が3日以上未解決 | 読めない箇所の一覧を作り、リーダーに質問の時間を頼む |
| 指摘も指示も来ない | 前週の週報が出ていない（仮） | 「問題ない」と受け取らず、自分から進捗と理解を見せて反応をもらう |
| 理解したことが形になっていない | 入場から5日たって、まとめを出していない | 小さくても「まとめ」を作って共有する |
| 指示を聞き逃したかもしれない | 判定しない（案内だけ） | 議事録とチャットを見直し、分からなければその場で確認する |
| 質問しにくい空気がある | 判定しない（案内と言い回し「暗黙の期待を言葉にする」） | 質問をまとめて「時間を決めて聞く」形に変える。違う人に聞くのも手 |
| 契約にない作業・責任を頼まれる | 判定しない（案内と、スコープ外 Issue の作成へ） | その場では引き受けず、自社の課長に相談する |
| 日々の指示者が体制図と違う | 判定しない（案内と、02_体制へ） | 実際の決裁の流れをメモし、自社に共有する |

## 受け入れ条件

1. 現場を作ると、docs 8区分と、チェックリストの 12 Issue・44項目（＋目標の1項目）がその現場に並ぶ
2. メンバーは段階ごとのチェックリストの進み具合を見て、項目を済みにできる
3. 作業 Issue の予定日・完了日から、進捗表に予定と実績の差が出る
4. 「読めない」Issue を作ると一覧に出て、2日で質問の目安が、3日で危険信号が出る
5. まとめの画面に、本人が書いた欄（全体像・担当機能の整理）と、用語集・未解決の質問・読めない一覧が並ぶ
6. 週報は4欄、課題 Issue は懸念の型で書ける
7. 意味が空の用語を登録でき、他の現場の会社公開された同じ語が見える（会社公開されていない語は見えない）
8. 言い回し集で、確認の言い回し8場面とワード確認表30語を引ける
9. 危険信号は7つすべて案内として出し、判定できる3つは条件に当てはまるときだけ強調する
10. アプリに載せたテンプレートの文言に、特定の顧客名・案件名が入っていない
11. 画面の約束の文言を「記録で人を採点しない」に改める
12. デモデータで、スライド7・12・15・16の内容を画面で説明できる

## 範囲外

- GitHub のテンプレートリポジトリ・同期（プロトタイプでは作らない）
- 目標・スキル項目・到達（spec 002）
- リーダーの受け取り画面（「読めない」の受け取り、まとめ確認など。spec 003）
- 体制のズレの件数など、マネジメント向けの数字（spec 004）
- 公開範囲の見直し（本人に選ばせない形への変更。spec 005）

## 未決事項（構想の持ち主に確認）

1. ~~チェックリストと言い回し集の元資料~~ → 「入場時チェックリスト上流編」「SI業界ワード確認表」を反映した
2. **危険信号の判定**：3日（読めない）と5日（まとめ）は元資料の日数に合わせた。「指摘も指示も来ない」を「前週の週報が出ていない」で判定するのは仮
3. **既存の文書の移し替え**：いまの7種類を docs 8区分へ移す対応（面談メモ → 00、作業範囲 → 01、体制 → 02、設計メモ → 04、議事録 → 05、週報 → 06、振り返り → 07。03_業務理解は新設）でよいか
4. **チェックリストの更新**：元資料を改訂したとき、作成済みの現場に反映するか（案：反映しない。新しく作る現場から新しい版を使う）

## 作ってみて分かったこと（構想に戻す）

1. **チェックリストは現場ごとか、人ごとか**：プロトタイプでは現場を作ったときに1組だけ並ぶ。あとから入場したメンバーにも入場時チェックリストは要るので、人ごとに並べるかを決めたい（GitHub なら、入場した人ごとに Issue を作るか、担当者を付けるか）
2. **まとめの危険信号はいつまで出すか**：「入場から5日たってまとめなし」は、入場からかなりたった人（途中から立場が変わったリーダーなど）にも出続ける。入場期（例：4週）だけに絞るかを決めたい
