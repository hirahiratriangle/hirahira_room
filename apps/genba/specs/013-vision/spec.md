## なぜ作るか

下から上への積み上げはつながったが、上から下への流れがなかった。ビジョンが働く画面に出ず、会社の重点が目標に届かず、アサインの判断が記録されず、構想の成長のループが閉じていなかった。

また、アプリは1現場1リポジトリで作られていたが、構想プレゼン（スライド2・5）はメンバー1人に1リポジトリとしている。構想に合わせた。

## 1メンバー1リポジトリ

- `MemberRepository`：人に1つ。現場が変わっても使い続ける
- `Site`：現場チーム（GitHub の Team）。リポジトリ名の欄を現場チーム名に改めた
- 記録は今までどおり site と author の組で持つ。これが「誰のリポジトリの、どの現場の分か」に当たる
- テンプレートの版はリポジトリの側に移した

## ビジョンの階層

| 階層 | 文言 | 出典 |
|---|---|---|
| 使命 | ITの力で世の中をより便利にして、人の心を豊かにする | 会社のホームページ |
| 経営理念 | 実務的で付加価値創造型の企業であり続け、ITシステムを駆使して社会全体を豊かにする | 会社のホームページ |
| ビジョン | 現場の時間を、実りあるものにする。 | 構想プレゼン 表紙 |
| 仕組み | 会社が人を支え、人の成長が会社を育てる | 構想プレゼン スライド5 |

文言は言い換えない。

## 上から下への流れ

使命 → ビジョン → 会社の重点 → メンバーの目標 → 成長 → アサイン → 次の成長

## 決めたこと

1. 全立場の職掌の画面の先頭に、ビジョンの階層・この立場の役割・会社の重点を出す
2. 会社の重点は会社が画面で決める。重点の年度の区切りは今は持たない
3. 目標を立てる画面で重点に★を付ける。選ぶのは本人
4. アサインはマネジメントが記録する。次の目標に合うかはマネジメントの判断で、自動では決めない
5. アサインすると、まだ入っていない現場にはメンバーとして入れる
6. 「成長の連鎖をお客様まで延ばす」案は採用しない（構想の持ち主の判断）

## 受け入れ条件

1. 1人のリポジトリは、現場が増えても1つ
2. 全立場の職掌の画面の先頭にビジョンの階層が出る
3. 会社だけが重点を変えられ、目標を立てる画面に届く。重点以外も選べる
4. 重点に向かう目標の割合と、目標に合うアサインの割合が出る
5. マネジメントだけがアサインを記録できる。Archive した現場へはアサインできない

## 作ってみて分かったこと（構想に戻す）

1. **KPI の目標値**：今もコードの仮の数字で、ビジョンから決まっていない。会社が画面で決める形は残っている
2. **改訂の提案の反映**：採用してもテンプレートには自動で入らない。テンプレートをコードで版管理しているため
3. **架空の会社と本物の理念**：デモの説明は架空の SI 会社だが、ビジョンの階層は実在の会社の言葉。公開する場合は説明を揃えたい
4. **本番の権限**：メンバー1人に1リポジトリでは、チームが読む権限を Team で与える。リポジトリの数は人数分になる
